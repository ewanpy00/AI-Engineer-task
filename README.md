# Metacritic Games Service

Тестовое задание, AI Automation Engineer.

**Демо:** [ai-engineer-task-production.up.railway.app](https://ai-engineer-task-production.up.railway.app/games)

## Что это

Сервис раз в час забирает новые игры с Metacritic, складывает их в Postgres и
показывает каталог: карточка с оценками по всем платформам, резюме отзывов
критиков и игроков от LLM, похожие игры, заключение по летсплею с YouTube.
Плюс страница мониторинга, на которой видно идущий обход.

Данные берутся из открытого JSON API `backend.metacritic.com`, HTML не
разбирается (почему — ниже, в «Как делался проект»).

## Что реализовано

| Часть ТЗ | Состояние |
|---|---|
| Часовой обход каталога | есть: New Releases, дальше SEE ALL по курсору дня, 20 игр за заход, повторов внутри суток нет |
| Список игр: поиск, фильтр по платформе, сортировка, пагинация | есть, всё через htmx-фрагмент без перезагрузки страницы |
| Карточка: описание, разработчик, издатель, ESRB, жанры, обложка, трейлер, Metascore и Userscore по каждой платформе | есть |
| Резюме отзывов критиков и игроков (LLM) | есть, два раздельных блока в карточке |
| Похожие игры | есть, top-5 из своей базы по пересечению жанров и совпадению разработчика |
| Доп. 2: мониторинг и кнопка запуска | есть: `/status` с живой лентой через SSE и ручным заходом |
| Доп. 1: летсплеи | есть: самый просматриваемый ролик ищется через `yt-dlp`, пересказ берётся у 300.ya.ru, заключение по нему делает модель; в карточке блок со ссылкой на ролик. Часть роликов сервис пересказать не берётся — такие игры остаются без блока |

Из плана не сделан T-49: ручной запуск не переклеймивает игры, упавшие
сегодня, — они переобработаются на следующие сутки.

## Архитектура

| Модуль | Что внутри |
|---|---|
| `app/clients/` | HTTP-клиент Metacritic: один `AsyncClient`, глобальный лимит 1 rps, retry с backoff, маппинг ответов в DTO |
| `app/ingest/` | заход: курсор дня, claim игр, выбор батча, upsert, оркестратор с advisory-локой |
| `app/llm/` | адаптер Gemini, загрузка промптов, JSONL-лог вызовов, пайплайн резюме отзывов |
| `app/letsplay/` | поиск ролика через yt-dlp, пересказ через 300.ya.ru, пайплайн летсплея |
| `app/web/` | страницы, htmx-фрагменты, SSE |
| `app/events.py`, `app/state.py` | шина событий обхода и состояние воркера, из которого рисуется `/status` |
| `schema.sql` | вся схема одним файлом, применяется при старте приложения; миграций нет |

Один заход: advisory-лока → батч игр → на каждую игру `product` плюс
Userscore по её платформам → upsert в транзакции → best-effort обогащение
(резюме отзывов, летсплей) → строка в `runs`. Падение одной игры не роняет
заход, а отказ LLM или летсплея не меняет статус самой игры: каталожная часть
уже в базе, обогащение дозаполнится следующим заходом.

Подробности и обоснование решений — в [`docs/10-design.md`](docs/10-design.md).

## Запуск

Нужны Python 3.12, [uv](https://docs.astral.sh/uv/) и Postgres 14+
(расширение `pg_trgm` ставится само вместе со схемой).

```bash
cp .env.example .env     # заполнить DATABASE_URL, ADMIN_TOKEN, GOOGLE_API_KEY, YA300_SESSION_ID
uv sync
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Схема накатывается при старте, отдельной команды миграции нет. Готовность —
`GET /healthz`, он же проверяет соединение с базой. Первого планового захода
можно не ждать:

```bash
curl -X POST localhost:8000/admin/run -H "X-Admin-Token: $ADMIN_TOKEN"
```

В контейнере:

```bash
docker build -t metacritic-digest .
docker run --env-file .env -p 8000:8000 metacritic-digest
```

### Переменные окружения

| Переменная | Обязательна | Зачем |
|---|---|---|
| `DATABASE_URL` | да | Postgres. Форма `postgresql://…` приводится к asyncpg сама |
| `ADMIN_TOKEN` | да | заголовок `X-Admin-Token` для `POST /admin/run`. Дефолта нет: с пустым значением ручка закрыта для всех |
| `GOOGLE_API_KEY` | для резюме | ключ Google AI Studio; без него резюме и заключения получают статус `llm_failed` |
| `YA300_SESSION_ID` | для летсплеев | сессионная кука 300.ya.ru; без неё летсплеи получают `service_error` с причиной `no_session` |
| `SCHEDULER_ENABLED` | нет (`true`) | часовой планировщик; выключается на время локальных прогонов |
| `LLM_ENABLED` | нет (`true`) | общий рубильник обращений к модели |
| `GEMINI_MODEL` | нет (`gemini-3.5-flash-lite`) | имя модели; от него не зависит ничего, кроме самого вызова |
| `LETSPLAY_ENABLED` | нет (`true`) | выключает поиск и пересказ летсплеев целиком |

Остальные (`METACRITIC_*`, `GEMINI_*`, `LETSPLAY_*` — троттлинг, таймауты,
лимиты) перечислены в [`.env.example`](.env.example) и
[`app/config.py`](app/config.py) со значениями по умолчанию.

## Работа с LLM

Промпты вынесены в [`prompts/`](prompts/) с версией в имени файла, в коде
только загрузка. Ответ забирается структурой, а не парсингом текста.

Отзывы пользователей — недоверенный ввод: цитаты идут отдельным сообщением
в `<review>`, системная часть промпта предписывает игнорировать инструкции
внутри.

Каждый вызов пишется в `logs/llm/YYYY-MM-DD.jsonl`, отдельная строка на
каждую попытку.

LLM-слой изолирован за интерфейсом `LlmClient`. Смена провайдера — один
адаптер; ретраи, circuit breaker и логирование провайдеро-независимы.

### Прогон, с которого собраны логи

Volume на Railway не покупали (OQ-3), поэтому raw-логи в репозитории — с
локального прогона на отдельной базе (T-48). Четыре часовых цикла подряд,
94 игры, 06.09.2026 21:21–22:10 UTC: три захода кнопкой `POST /admin/run`
и четвёртый — плановый, от cron `0 * * * *`.

| Заход | Триггер | Игр | Провалено | Вызовов LLM | Неудачных | Время |
|---|---|---|---|---|---|---|
| 1 | manual (фаза `new_releases`) | 20 | 0 | 46 | 4 | 4:49 |
| 2 | manual (`browse`, offset 0) | 20 | 0 | 8 | 0 | 6:20 |
| 3 | manual (`browse`, offset 20) | 20 | 0 | 8 | 0 | 6:37 |
| 4 | schedule (`browse`, offset 40) | 34 | 0 | 12 | 0 | 10:07 |

Итог в логе — 85 строк: 25 `review_summary_critic.v1`, 15
`review_summary_user.v1`, 45 `letsplay_conclusion.v1`. Логических вызовов
модели за ними 74, неудачей закончились 4. Семь первых попыток упёрлись в
`429`, три из них добрал ретрай, оставшиеся четыре исчерпали все три попытки:
две легли в `review_summaries.status='llm_failed'`, две — в
`letsplays.status='service_error'`, и следующий заход возьмётся за них снова.
Circuit breaker ни разу не открылся. Токенов 119 242 на вход и 12 370 на
выход, медианная задержка успешного вызова 1,66 с.

Проверка лога (структура design §5.4 плюс правило «отзывы — не инструкции»:
system-сообщение обязано совпадать с телом файла промпта, а `prompt_sha256` —
с хешем файла) прошла на всех 85 строках без нарушений.

Что видно из цифр: почти все вызовы модели приходятся на первый заход, потому
что отзывы есть только у игр из New Releases. Дальше `browse` идёт по
`sortBy=-releaseDate` — сначала анонсы с будущими датами, потом поток мелких
релизов, у которых на Metacritic нет ни строчки; такие игры честно получают
`review_summaries.status='no_data'` и модель не зовут вовсе (154 строки из
188). Часовой обход при этом не простаивает: каталожная часть и летсплей
собираются всё равно.

## Безопасность

Модель угроз простая: сервис ходит в четыре чужие системы (Metacritic,
YouTube, 300.ya.ru, Google AI Studio) и показывает результат в открытом вебе.
Всё, что приходит оттуда, считается недоверенным вводом, а наружу не должно
утекать ничего, кроме самого каталога.

**Что чем закрыто**

- `POST /admin/run` — общий секрет в заголовке `X-Admin-Token`, сравнение
  постоянным временем по байтам. Пустой `ADMIN_TOKEN` закрывает ручку целиком:
  незаполненная переменная — это не «разрешить всем». CSRF ей не грозит:
  кастомный заголовок нельзя послать простой формой с чужого сайта.
- `/status` и `/events` открыты (ТЗ требует мониторинг в веб-интерфейсе), но
  секретов и текстов исключений на них нет. Токен для кнопки вводится в поле
  на странице и уходит только в заголовке запроса. В ленте и в журнале заходов
  видна машинная причина отказа (`MetacriticError`, `no_session`), а полный
  текст остаётся в `runs.error`, `processed_games.error` и в логе процесса —
  в нём хосты, пути и параметры запросов. `GET /healthz` по той же причине
  отвечает `{"status":"error","db":false}` без текста ошибки БД.
- SQL — только параметризованный. Единственная динамика в запросах —
  фрагмент `ORDER BY`, и он берётся из белого списка `_SORT_SQL`, а не из
  query-строки. Поисковый запрос экранируется под `ILIKE` (`\`, `%`, `_`).
- Шаблоны рендерятся с автоэкранированием Jinja, `|safe` в проекте нет.
  Ссылки из чужих ответов (`games.video_url`) проходят проверку схемы и на
  границе с API, и в шаблоне: в `<iframe src>`/`<a href>` попадает только
  http(s), иначе блок не рисуется вовсе — `javascript:` там исполнился бы в
  origin страницы.
- Отзывы, пересказы летсплеев и названия игр — недоверенный ввод: уходят в
  модель отдельным `user`-сообщением, обёрнутым в `<review>`/`<retelling>`, с
  экранированием угловых скобок; в system-промпт не попадают никогда. Сам
  промпт предписывает игнорировать инструкции внутри тегов.
- Кука 300.ya.ru отправляется только на сам 300.ya.ru: у клиента выключены
  редиректы. httpx хранит куку из словаря без домена, и редирект на сторонний
  хост унёс бы туда доступ к аккаунту Яндекса целиком.
- Секреты живут только в окружении. `.env` в git не попадал ни разу и
  исключён из образа; в контейнере процесс работает под непривилегированным
  uid 10001 и на запись ему отдан только `logs/` — код и venv принадлежат root.

**Чего осознанно нет** — см. «Ограничения» ниже.

## Ограничения

- Пересказ летсплеев держится на 300.ya.ru — неофициальном сервисе без
  публичной документации, с сессионной кукой вместо ключа. Контракт снят с
  живого API 07.09.2026 и описан в docstring `app/letsplay/retelling.py`;
  сменить его могут без предупреждения, а кука рано или поздно протухнет —
  тогда игры получат `service_error` с причиной `auth`. Часть роликов сервис
  не осиливает и сам (отвечает `status_code=2`) — такая игра остаётся без
  блока в карточке; на прогоне T-48 сервис отказал на 52 роликах из 92
  найденных, пересказ получили 40. Всё это штатная деградация: карточка без летсплея —
  нормальное состояние (ADR-8), остальная обработка не страдает.
- Поиск ролика (`yt-dlp ytsearch`) локально работает, но с датацентрового IP
  YouTube может отвечать `LOGINREQUIRED` (ADR-8) — тогда игры на проде получат
  `not_found`. Это видно на `/status` и в таблице `letsplays`.
- Бесплатный тир Google AI Studio считает квоту отдельно по каждой модели.
  У `gemini-3.5-flash-lite` упирается минутный лимит — 15 запросов. Backoff
  разбирает почти всё: на прогоне T-48 до отказа дошли 4 вызова из 74,
  следующий заход пробует их снова.
- Persistent volume на Railway не покупали (OQ-3): `logs/llm/*.jsonl` на проде
  живут до редеплоя, полные raw-логи вызовов собираются с локального прогона
  (см. «Прогон, с которого собраны логи»).
- Один инстанс приложения. Advisory-лока не даёт заходам наложиться, но
  планировщик, курсор дня и claim рассчитаны именно на один процесс.
- Аутентификации в сервисе нет: единственный секрет — общий `ADMIN_TOKEN` на
  `POST /admin/run`, ролей и учётных записей не заводили. `/status` открыт
  всем: по нему видно, что сервис сейчас делает и сколько игр обработал за
  сутки. Секретов и текстов исключений там нет (см. «Безопасность»), но сам
  факт работы воркера — публичный.
- CSP и прочих security-заголовков нет, htmx и его SSE-расширение грузятся с
  `unpkg.com` без `integrity`. Подмена пакета на CDN дала бы полный контроль
  над страницей. Для демо принято как есть; на реальном проде — свой хостинг
  скриптов или SRI плюс CSP.
- Ограничения частоты нет ни на одной ручке. Число SSE-подписок на `/events`
  не ограничено, каждая держит очередь событий в памяти процесса.
- `logs/llm/*.jsonl` закоммичены в репозиторий (ТЗ требует raw-логи, а volume
  на Railway не покупали). Секретов в них нет, но логгер пишет `messages`
  целиком и без фильтрации, ротации и потолка размера — на реальном проде
  логи должны уезжать во внешнее хранилище, а не в git.
- `games.raw` хранит полный ответ product на каждую игру (design §3.1, «для
  дебага») — без TTL и без ограничения размера. При долгой работе таблица
  растёт быстрее полезных данных; менять это — решение стадии design, а не
  правка на месте.
- Обложки отдаёт CDN Metacritic по `bucketPath`, локально ничего не хранится:
  если картинка уедет у них, она пропадёт и здесь.
- Примерно у четверти игр обложки нет вовсе, и это данные источника, а не
  потеря по дороге. Проверено 07.09.2026: на проде 35 карточек из 145 (24%)
  без картинки, при этом все 93 собранных с сайта URL обложек отдают 200 и
  `image/jpeg` — и анонимно, и с браузерным `Referer` домена прода:
  хотлинк-защиты у Metacritic нет. У всех игр без обложки ответ `product` содержит
  пустой `images: []`, в листинге каталога у них же `image: null` — брать
  картинку неоткуда. Выборка не случайная: ни у одной из этих игр нет ни
  Metascore, ни Userscore, и все они вышли на днях. Сервис по ТЗ ходит
  `sortBy=-releaseDate`, то есть систематически собирает тот край каталога,
  который Metacritic ещё не наполнил. На первой странице списка (сортировка
  «сначала новые») доля пустых поэтому заметно выше средней — 10 из 24.
  Обложка дозаполняется сама, пока игра держится в начале листинга: обход
  каждые сутки стартует с `offset=0`, а `upsert_game` перезаписывает
  `cover_path` на каждом проходе. Игра, получившая артворк позже, когда она
  уже ушла из зоны дневного обхода, останется без него. Убрать пустые плитки
  из списка можно фильтром `metaScoreMin=1` в `list_browse` — тем же, что уже
  стоит в `list_new_releases`, — но это обмен полноты каталога на внешний вид,
  и решение продуктовое, а не техническое.

## Тесты

```bash
uv run pytest
```

Тестам нужен живой Postgres из `DATABASE_URL`: там, где проверяются `ON
CONFLICT`, advisory-лока и статусы, база настоящая, а внешние сервисы
подменены. Без базы такие тесты помечаются `skipped`, остальные проходят.

## Деплой

Railway, `Dockerfile` + `railway.json`. Один инстанс: планировщик, курсор дня и claim рассчитаны на один процесс.
