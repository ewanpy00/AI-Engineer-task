Стадия: research. Не содержит архитектурных решений — только факты и ASSUMPTION.
Дата проверки фактов: 2026-09-06 (см. RFC3339 в docs/00-research.json).
Среда проверки: обычная рабочая машина разработчика (не облачный сервер), curl 8.x,

## 0. Самое рискованное: отдаётся ли контент вообще

Да, отдаётся, причём двумя способами:

1. `www.metacritic.com/*` — обычный SSR HTML (Nuxt 3 / Vue, **не Next.js**, вопреки
   формулировке задания). Контент вшит в HTML на сервере.
2. `backend.metacritic.com/*` — **открытый JSON API без ключа**, которым сам сайт
   пользуется на клиенте (SSR делает те же запросы). Он оказался значительно проще
   и надёжнее, чем парсинг HTML, и именно на нём стоит строить интеграцию.

Проверено:
```
curl -sI https://www.metacritic.com/game/            → HTTP/2 200
curl -s  https://backend.metacritic.com/finder/metacritic/web?sortBy=-releaseDate&offset=0&limit=5&mcoTypeId=13
                                                      → HTTP/2 200, валидный JSON
```
Никаких капч/JS-челленджей на первом запросе нет. 403 бывает, но точечно (см. §4).

## 1. Архитектура сайта: HTML+SSR-хидрация или чистый JSON

**Факт (ASSUMPTION в задании неверна):** сайт построен на **Nuxt 3 (Vue)**, а не
Next.js. `__NEXT_DATA__` на странице нет вообще. Вместо него —
`<script type="application/json" id="__NUXT_DATA__" data-ssr="true">`.

```
grep -o "__NEXT_DATA__" game_root.html   → пусто
grep -o 'id="__NUXT_DATA__"' game_root.html → найдено
```

Формат данных внутри `__NUXT_DATA__` — не обычный JSON-объект, а «плоский» массив
в формате библиотеки `devalue` (числа — это индексы-ссылки на другие элементы
массива, обёртки вида `["ShallowReactive", <idx>]` для реактивных Vue-объектов).
Раскодировать вручную нереально, но раскодируется однозначно и полностью через
npm-пакет `devalue` с несколькими identity-ревайверами
(`ShallowReactive`, `ShallowRef`, `Reactive`, `Ref`, `EmptyRef` и т.п.):

```js
import { parse } from 'devalue';
const revivers = Object.fromEntries(
  ['ShallowReactive','ShallowRef','Reactive','Ref','EmptyRef','EmptyShallowRef']
  .map(t => [t, v => v])
);
const data = parse(rawScriptText, revivers); // получили полноценный JS-объект
```
Проверено на трёх страницах (`/game/`, `/browse/game/all/all/all-time/new/`,
`/game/onimusha-way-of-the-sword/`) — разбор проходит без ошибок, значения совпадают
с тем, что видно на странице глазами.

**Вывод:** парсинг HTML/`__NUXT_DATA__` — рабочий, но второй по приоритету способ
(нужен node-рантайм или Python-порт алгоритма devalue). Первый по приоритету —
прямой вызов `backend.metacritic.com`, см. ниже: он отдаёт **чистый, стабильный JSON**
без всякой девалью-магии и вообще без специфичных для UA блокировок (см. §4).

Внутри `__NUXT_DATA__` полезные ключи (если решат парсить HTML как fallback):
- страница `/game/` → `data["loadPage:door:games-door-global:"].components[]`,
  внутри — блок с `meta.componentName === "new-releases-carousel"`.
- страница `/browse/game/all/all/all-time/new/[N]/` →
  `data["browse-game-/browse/game/all/all/all-time/new/[N==1?'':N]/"]` (ключ буквально
  содержит путь страницы) → `{items:[...], total: N}`.
- страница карточки игры → `data["loadPage:games:<slug>:"]` (не разбирался до конца,
  т.к. прямой API проще).

## 2. Прямой JSON API (`backend.metacritic.com`) — основной способ

Это тот же API, которым пользуется фронтенд (Nuxt делает к нему `useFetch` и на
сервере, и на клиенте). Ключ (`apiKey=...`) иногда присутствует в URL, но **не
обязателен** — все нижеперечисленные эндпоинты отвечали 200 и без него.

### 2.1 Первые 20 игр (раздел New Releases на `/game/`)

```
GET https://backend.metacritic.com/finder/metacritic/web
    ?componentName=new-releases-carousel&componentType=ProductList
    &sortBy=-releaseDate&metaScoreMin=1&offset=0&limit=20&mcoTypeId=13
```
Проверено: `data.items[]` (ровно 20 элементов) **дословно совпадает** по составу
и порядку с блоком «New Releases»/`componentName=new-releases-carousel`, который
приходит внутри `__NUXT_DATA__` при обычной загрузке `/game/`. Значит эндпоинт
можно дёргать напрямую, не открывая HTML вообще.

- `mcoTypeId=13` = games (эмпирически подтверждено, других значений не проверял).
- `metaScoreMin=1` — фильтр, отсекающий игры без единого критического обзора.
  Из-за этого «New Releases» ⊂ «SEE ALL» (второе не фильтрует по score).
- `data.totalResults` = 18524 на момент проверки (с учётом фильтра `metaScoreMin=1`).

### 2.2 Раздел SEE ALL (сортировка «Новые»), пагинация

Реальный вызов, которым пользуется страница
`https://www.metacritic.com/browse/game/all/all/all-time/new/2/`
(подтверждено побайтовым совпадением первых 5 тайтлов):
```
GET https://backend.metacritic.com/finder/metacritic/web
    ?sortBy=-releaseDate&offset={page*24}&limit=24&mcoTypeId=13
```
(без `metaScoreMin` — попадают и игры без оценок, `sentiment:"tbd"`, `score:null`).

- Размер страницы в UI сайта — **24**, не 20 (это не мешает вашему сервису забирать
  свои 20 через `limit=20` — параметр `limit` этим эндпоинтом честно уважается,
  проверено `limit=5/20/24/50`).
- `data.total` = 177895 на момент проверки (весь каталог игр, огромное число из-за
  DLC/переизданий/малоизвестных инди без обзоров).
- **РИСК (см. RISKS #1):** сортировка по `releaseDate` не даёт стабильного tie-break
  для игр с одинаковой датой выхода. Два запроса `offset=0` подряд совпали, но
  ручной расчёт `offset=24` не совпал с реальной страницей 2, снятой минутой позже
  (см. сырые данные — `browse_guess.json` vs `browse_all_p2.html`, разные наборы игр
  на границе страницы). На практике это значит: нельзя полагаться на "offset -
  это надёжный курсор между двумя отдельными обходами"; дедуп нужно делать по
  стабильному `id`/`slug`, а не по номеру страницы.

### 2.3 Карточка игры — почти всё одним запросом

```
GET https://backend.metacritic.com/games/metacritic/{slug}/web?componentName=product&componentType=Product
```
Возвращает `data.item` со всем нужным, кроме юзер-скора (см. 2.4) и без сводки по
отзывам текстом (см. §3). Пример реального ответа (обрезано) — `product.json`
в рамках этого исследования, поля:

| Поле ТЗ | JSON-path в ответе | Комментарий |
|---|---|---|
| Название | `data.item.title` | строка |
| Обложка | `data.item.images[].bucketPath` (typeName `cardImage`/`mainImage`) | см. §2.5 про URL |
| Платформа(ы) | `data.item.platforms[].name` / `.slug` | массив, у Onimusha — 4 шт. |
| Metascore по платформе | `data.item.platforms[].criticScoreSummary.score` (+`.reviewCount`,`.sentiment`) | уже готово, доп. запрос не нужен |
| Userscore по платформе | **отсутствует в этом ответе**, нужен отдельный вызов, см. 2.4 | |
| Разработчик | `data.item.production.companies[?(@.typeName=='Developer')].name` | там же `Publisher` |
| Описание | `data.item.description` | обычный текст с `\r\n`, HTML-тегов нет |
| Видео (офиц. трейлер) | `data.item.video.embedUrl` / `.manifestUrl` (HLS m3u8, JW Player) | это **трейлер Metacritic, не летсплей с YouTube** — отдельная задача, см. §5 |
| Жанры | `data.item.genres[].name` | пригодится для «похожих игр» |
| Рейтинг ESRB | `data.item.rating` | "M", "E" и т.д. |

CSS-selector fallback (на случай, если решат парсить голый HTML без JS):
заголовок — `h1.hero-title__text`; `<meta property="og:title">` тоже есть.
Полного маппинга остальных полей через CSS не делал — JSON-путь надёжнее и дешевле.

### 2.4 Userscore (по каждой платформе — отдельный вызов)

```
GET https://backend.metacritic.com/reviews/metacritic/user/games/{slug}/platform/{platform-slug}/stats/web
GET https://backend.metacritic.com/reviews/metacritic/critic/games/{slug}/platform/{platform-slug}/stats/web
```
`{platform-slug}` берётся из `platforms[].slug` карточки игры (`pc`, `playstation-5`,
`xbox-series-x`, `nintendo-switch-2`, ...).
Ответ: `data.item.score` (0–10 для user, 0–100 для critic), `.reviewCount`,
`.sentiment`, `.positiveCount/.neutralCount/.negativeCount`.

Важно: если вызвать **без** `/platform/{slug}/` в пути, эндпоинт возвращает данные
только «ведущей» платформы (`isLeadPlatform: true` в карточке игры), а не агрегат по
всем. Проверено параметром `?platform=pc` в query-string — **игнорируется**,
платформа определяется только сегментом пути.

### 2.5 Обложка — прямой URL без подписи

```
https://www.metacritic.com/a/img/{bucketPath}
```
`{bucketPath}` — из `images[].bucketPath`, например `/provider/7/2/7-1781631535.jpg`.
Проверено: отдаёт **оригинальный загруженный файл** (реально скачал, размеры
совпали 1:1 с `images[].width/height` из API — 226×332).

Есть также CDN-вариант с ресайзом:
`https://www.metacritic.com/a/img/resize/{hash}/catalog{bucketPath}?width=&height=&fit=...`
— но `{hash}` это подпись, привязанная к конкретным `width`/`height`. Проверено:
подмена `width`/`height` при том же `hash` → `403`. То есть **произвольный ресайз
конструировать нельзя**, а вот безусловный оригинал по первому URL — можно и нужно.

### 2.6 «Похожие игры» от самого Metacritic (для контраста с §6)
```
GET https://backend.metacritic.com/finder/metacritic/web
    ?sortBy=-metaScore&mcoTypeId=13&genres=Action+Adventure&offset=0&limit=24
    &componentName=related-carousel
```
Это подбор Metacritic по жанру среди **всего** их каталога, не среди вашей БД —
для задачи "похожие игры среди уже загруженных" бесполезен напрямую, но подтверждает,
что жанр — единственный явный сигнал похожести, который отдаёт сайт.

## 3. Отзывы

### 3.1 Общее устройство

Критики и пользователи — **полностью раздельные** сущности (разные URL, разные
шкалы: critic 0–100, user 0–10), и **обе разбиваются по платформе** — то есть у
игры с 4 платформами теоретически 4×2 = 8 независимых наборов отзывов + сводок.

Списки отзывов с текстом (`quote`):
```
GET https://backend.metacritic.com/reviews/metacritic/critic/games/{slug}/platform/{p}/web
    ?offset=0&limit=10&filterBySentiment=all&sort=date&componentType=ReviewList
GET https://backend.metacritic.com/reviews/metacritic/user/games/{slug}/platform/{p}/web
    ?offset=0&limit=50&filterBySentiment=all&sort=date&componentType=ReviewList
```

**Проверенные лимиты страницы (важно для оценки числа запросов):**
- Критики: `limit` игнорируется сервером, **всегда ровно 10** элементов на
  странице, независимо от того, передать 10/20/50/100. Реальная страница сайта
  так и пагинирует (`offset=0,10,20...90` для игры с 92 обзорами).
- Пользователи: `limit` реально уважается, проверено вплоть до `limit=1000`
  (Elden Ring, 6593 отзыва). `limit=5000` → HTTP 500 upstream error
  (`SyntaxError: "upstream r..."`) — где-то между 1000 и 5000 есть server-side
  потолок, точное число не установлено. Дефолт на сайте — 50.

**Несовпадение счётчиков (важный нюанс для сумморизации):** `reviewCount` в
`.../stats/web` считает **все оценки**, включая оценки без текста; `totalResults`
в списке `.../web` считает только записи с `quote`. Пример (Onimusha, платформа PC):
stats → `reviewCount=11`, список отзывов → `totalResults=5`. Для генерации резюме
"что нравится/не нравится" доступны только эти 5, а не 11.

### 3.2 Готовые сводки-«вырезки» (может заменить часть пайплайна суммаризации)

Отдельный, не документированный публично, но рабочий эндпоинт:
```
GET https://backend.metacritic.com/reviews/metacritic/critic/games/{slug}/summary/web
GET https://backend.metacritic.com/reviews/metacritic/critic/games/{slug}/platform/{p}/summary/web
GET https://backend.metacritic.com/reviews/metacritic/user/games/{slug}/summary/web
```
Возвращает `data.item.{default,positive,negative,neutral}` — уже разложенные по
тональности подборки цитат (проверено: critic — 7/7/0/7, user — 7/7/2/1 шт. по
корзинам для Onimusha). Это готовый, уже отфильтрованный по сентименту материал
для LLM-суммаризации без необходимости пагинировать весь список и считать score
самостоятельно. **Оговорка:** без `/platform/{slug}/` отдаёт сводку только по
ведущей платформе, как и `stats`.

### 3.3 Раздельность критиков/пользователей на UI
Подтверждено структурой URL сайта: `/game/{slug}/critic-reviews/` и
`/game/{slug}/user-reviews/` — два разных маршрута с разными фильтрами
(`filterBySentiment`, `sort=date|score|publication`), полностью раздельные данные.

## 4. Anti-bot, заголовки, rate limit

**Факт, проверенный многократно и воспроизводимо:**
`www.metacritic.com` (HTML) стоит за Cloudflare с точечным WAF-правилом, которое
блокирует конкретные строки User-Agent библиотек по умолчанию:

```
curl -A "python-requests/2.31.0" https://www.metacritic.com/game/  → 403
  тело: "You are not allowed to access this resource" (text/plain, без JS-челленджа)
curl -A "Java/17.0.1"            https://www.metacritic.com/game/  → 403
```
Но при этом проходят **без каких-либо специальных заголовков**:
```
curl (дефолтный UA curl/8.x)                → 200
curl -A "" (пустой UA)                      → 200
curl -A "Mozilla/5.0 ... Chrome/120"        → 200
curl -A "Googlebot/2.1"                     → 200
curl -A "node-fetch"                        → 200
curl -A "Scrapy/2.11"                       → 200
curl -A "Go-http-client/1.1"                → 200
curl -A "okhttp/4.9.0"                      → 200
```
Вывод: это не защита от ботов вообще, а блок-лист конкретных «известных» строк
(`python-requests`, `Java/`). **Практическая рекомендация для реализации:** если
клиент на Python — обязательно переопределить `User-Agent` у `requests`/`httpx`
(иначе гарантированный 403 на HTML-страницах); достаточно любой не-дефолтной
строки, спуфить полноценный Chrome не обязательно (Scrapy/okhttp/curl тоже прошли).

`backend.metacritic.com` (JSON API) — **в наших тестах не блокировал вообще ни по
одному UA**, включая `python-requests` и `Java/17.0.1` (200 во всех случаях). Ещё
один довод в пользу прямого API как основного источника.

**Rate limit:** ни разу не встретили 429 и не нашли `x-ratelimit-*` заголовков.
Пробовали burst 20 запросов к `backend.metacritic.com` и 15 к `www.metacritic.com`
почти без паузы — все 200. Ответы `backend.metacritic.com` кешируются на
Cloudflare edge (`cf-cache-status: HIT`, `age: N`, `cache-control: public, max-age=600`
на некоторых роутах) — то есть повторные одинаковые запросы почти бесплатны для
источника.

**ASSUMPTION** (не проверено, т.к. не хотел получить реальный бан IP во время
исследования): это недокументированный приватный API, официального SLA/лимита нет.
Разумно закладывать консервативный лимит (например ≤ 1 запрос/сек с экспоненциальным
backoff на не-200/5xx) и мониторить долю ошибок в проде, а не полагаться на то, что
«тестами замечено 200 при 20 запросах» будет верно всегда.

`robots.txt` (реально получен) явно запрещает известных краулеров (AhrefsBot, GPTBot,
SemrushBot и др.) и пути `/search`,`/signup`,`/login`,`/user`,`/jl/`, но **не запрещает**
`/game/*` и `/browse/*` для `User-agent: *`. Это не юридическая консультация и не
отменяет возможные ограничения ToS Metacritic на автоматический сбор данных — это
вне зоны research-стадии, отмечаю как факт из robots.txt, а не как разрешение.

## 5. YouTube: транскрипт летсплея

### 5.1 С официальным ключом (YouTube Data API v3)

Поиск видео — рабочий и дешёвый путь:
```
GET https://www.googleapis.com/youtube/v3/search?part=snippet&q={query}&type=video
    &order=viewCount&videoDuration=long&key={API_KEY}
```
Подтверждено официальной документацией Google (получено через доступ к
`developers.google.com`, не через collection memory):
- `order` поддерживает `viewCount` — «от большего числа просмотров к меньшему»
  (полезно, чтобы найти «самый популярный летсплей», как просит ТЗ).
- `search.list` **не возвращает** статистику просмотров в ответе — только snippet.
  Для реального `viewCount` нужен ещё `videos.list?part=statistics` по найденным ID.
- Квота: `search.list` стоит **100 unit за вызов**; дефолтная дневная квота проекта —
  **10 000 unit/день** ⇒ **не более 100 поисковых запросов в день** на один API-ключ
  (кросс-проверено через web-поиск, несколько независимых источников 2026 года
  сходятся на этой цифре). `videos.list` дешевле — 1 unit за вызов.

**Критичный факт, подтверждённый напрямую через официальную документацию Google**
(`developers.google.com/youtube/v3/docs/captions/download`): метод
`captions.download` **требует OAuth и прав редактирования видео** — то есть скачать
чужие субтитры (субтитры блогера с летсплеем) через официальный API **нельзя в
принципе**, ключом API это не обходится ни при каких условиях. Официальный ключ
может помочь только с **поиском** видео, но не с получением текста транскрипта.

### 5.2 Без ключа

Два практических варианта, оба сводятся к скрапингу — то, от чего официальный API
явно отгорожен:

**a) Прямой скрапинг таймд-текста (`youtube_transcript_api`-подобный подход).**
Механизм: страница `watch?v=...` содержит в `ytInitialPlayerResponse` подписанные
URL вида `https://www.youtube.com/api/timedtext?...&signature=...`. Проверено лично:
```
curl (обычный, без cookies/JS) на подписанный timedtext-URL → HTTP 200, но тело
пустое (0 байт) — типичный симптом блокировки не-браузерного/дата-центрового клиента.
```
Это воспроизводится стабильно и совпадает с задокументированной проблемой
библиотеки `youtube-transcript-api` (`jdepoix/youtube-transcript-api`, issue #511 и
др.): YouTube блокирует запросы с IP облачных провайдеров (AWS/GCP/Azure/DO) по
ASN, вне зависимости от частоты запросов — то есть блок может сработать с первого
же вызова.

**b) `yt-dlp` (скачивание готовых/автоматических субтитров или аудио для STT).**
Проверено лично и успешно **с обычной (не дата-центровой) машины**:
```
yt-dlp --skip-download --write-auto-sub --sub-lang en --sub-format vtt <url>
→ реально скачался валидный .vtt с текстом
```
Но в логе видно: `[jsc:deno] Solving JS challenges using deno` — начиная с 2025–2026
YouTube требует прохождения JS-челленджа/"PO token" для выдачи субтитров и
видео-потоков; `yt-dlp` решает это через встроенный плагин, которому нужен внешний
JS-рантайм (в тесте использовался `deno`, установленный отдельно). Подтверждено
многочисленными источниками (GitHub issues yt-dlp 2026 года, `PO Token Guide`):
именно дата-центровые IP (AWS/GCP/Azure/Hetzner/DO — их диапазоны публично известны)
получают `LOGINREQUIRED` от YouTube ещё на этапе получения ссылок на форматы, **до**
любых PO-token манипуляций — то есть даже `yt-dlp` с решением JS-челленджа может не
спасти на типичном облачном сервере.

**Поиск видео без ключа** тоже возможен через `yt-dlp` (`ytsearch{N}:{запрос}`) —
проверено лично, реально нашёл 5 летсплеев по запросу
`"Onimusha Way of the Sword let's play"` с полями `id/title/view_count/duration` без
единого API-ключа и без квот. Тот же риск блокировки по IP, что и в (a)/(b).

**Оценка времени интеграции** (ASSUMPTION, основано на объёме проверенных технических
шагов, не на реальной разработке):
- Поиск через официальный API (ключ, `search.list`+`videos.list`) — простая часть,
  1–2 часа, но с жёстким потолком 100 поисков/сутки, что при 20 играх/час
  (потенциально до ~480/сутки) кванты **не хватит** без кэширования/дедупа запросов.
- Получение транскрипта (без ключа, единственный доступный путь) —
  `yt-dlp` + автосабы, с фолбэком на отсутствие субтитров: минимум 3–5 часов на
  рабочую интеграцию + Docker-образ с `deno`, ещё время на обработку блокировок в
  проде (retry/proxy) сверху, по факту не оценено — зависит от IP хостинга.
- STT (Whisper и т.п.) поверх скачанного аудио как fallback, если у видео вообще нет
  субтитров — отдельная, более дорогая по времени и вычислениям ветка, не пробовал
  вживую в рамках этого исследования (ASSUMPTION по типовым оценкам — открытая
  модель whisper "base/small" на CPU обрабатывает ролик медленнее реального времени,
  на 10–20 минутный летсплей это минуты-десятки минут CPU-времени на видео).

## 6. Похожие игры — 2-3 подхода за день, без рекомендации

Только факты и стоимость, выбор — не моя стадия.

**A. По жанру/разработчику из уже собранных данных (без внешних вызовов).**
Данные уже есть в БД после обычного скрапинга карточки игры: `genres[]` и
`production.companies[typeName=Developer]` (см. §2.3). Похожесть = пересечение
множеств жанров (+ опционально совпадение разработчика/платформы) среди игр, уже
загруженных в свою БД. Стоимость: не требует новых вызовов к внешним API,
реализуется SQL-запросом/фильтрацией в памяти. Проверено, что поле `genres` почти
всегда непустое (1+ жанр на игру, видел до нескольких в других тестовых ответах).

**B. Векторные эмбеддинги описания (`description`).**
Эмбеддинг через внешний сервис (например, OpenAI Embeddings API) или локальную
модель (`sentence-transformers`), косинусное сходство между играми в своей БД.
Стоимость: 1 вызов эмбеддинга на игру при сохранении + хранение вектора (pgvector
либо просто в памяти при небольшом размере БД за 1 день — десятки-сотни записей) +
код подсчёта top-N похожих. Не проверялось вживую (нет доступа к ключу эмбеддингов
в рамках research) — ASSUMPTION по типовой стоимости такой интеграции.

**C. Использовать «related-carousel» самого Metacritic (см. §2.6) и пересечь с
локальной БД.** Технически тривиально (ещё один GET, уже проверенный рабочим), но
даёт результат только если у похожих по мнению Metacritic игр найдётся пересечение
со списком уже загруженных вами игр — при небольшой БД (только что запущенный
сервис, 20–500 игр за день) пересечение скорее всего будет частым нулём, потому что
Metacritic подбирает похожие из **всего** своего каталога (сотни тысяч игр), а не из
вашей выборки. Стоимость реализации минимальна, но результат зависит от того, сколько
у сервиса уже накоплено данных.

## RISKS

1. **Нестабильная сортировка при пагинации "новых" игр.** `sortBy=-releaseDate` не
   имеет детерминированного tie-break для игр с одинаковой датой — подтверждено
   расхождением расчётного `offset=24` с реальной страницей 2 при повторном опросе.
   Значит "очередная страница" по номеру может пропустить/задвоить игру между двумя
   часовыми обходами. Нужен дедуп по стабильному `id`, а не по номеру страницы/offset.
2. **YouTube — вообще нет надёжного способа получить транскрипт с типичного
   облачного сервера.** Официальный API не отдаёт чужие капшены ни при каких
   условиях (OAuth + права владельца видео). Неофициальный путь (timedtext/yt-dlp)
   у меня лично **не сработал** через голый curl (пустой ответ) с этой машины и,
   по документированным источникам (issues yt-dlp/youtube-transcript-api 2026 г.),
   систематически блокируется именно на IP-диапазонах AWS/GCP/Azure/Hetzner/DO —
   то есть именно там, где обычно живёт продовый сервер. Работоспособность зависит
   от хостинга и требует прокси/JS-рантайма (deno), что добавляет инфраструктурной
   сложности, не упомянутой в ТЗ.
3. **Квота YouTube Data APIv3 (100 search.list/день) несовместима "в лоб" с темпом
   20 игр/час.** При 20 новых играх в час и 1 поиске на игру потолок исчерпывается
   в течение ~5 часов работы, если не кэшировать/не переиспользовать запросы и не
   искать альтернативы поиску через ключ.
4. **Отсутствие официального rate-limit для backend.metacritic.com.** Это приватный,
   не задокументированный API. Поведение при устойчивой промышленной нагрузке (а не
   разовых тестовых всплесках по 20-35 запросов) не проверялось и может измениться
   без предупреждения (в т.ч. полное закрытие анонимного доступа).
5. **www.metacritic.com блокирует по имени библиотеки, не по паттерну поведения.**
   Пока это тривиально обходится (см. §4), но это WAF-правило может расшириться
   Cloudflare/Metacritic в любой момент на более общий anti-bot без предупреждения —
   в отличие от backend.metacritic.com, у которого пока подобной защиты не увидел
   вовсе (что тоже может измениться).
6. **Расхождение "оценок" и "отзывов с текстом".** `reviewCount` в сводке и
   `totalResults` в списке отзывов — разные числа (см. §3.1). Если ожидать, что
   "отзывов N" ⇒ "текстов для суммаризации N", легко получить пустую/урезанную
   выборку для суммаризации у игр с малым числом письменных отзывов.
7. **HTML-страницы (`www.metacritic.com`) используют Nuxt/devalue, а не Next.js**,
   что делает более простой путь (прямой JSON API) единственно разумным — попытка
   парсить HTML/`__NEXT_DATA__` по описанию из ТЗ уткнётся в несуществующий тег.

## Топ-5 фактов, сильнее всего влияющих на архитектуру

1. **Есть открытый недокументированный JSON API `backend.metacritic.com`** — без
   ключа, без UA-блокировок, отдаёт данные структурированно и с CDN-кэшем. Это
   должен быть основной источник данных сервиса, а не HTML-скрапинг с парсингом
   Nuxt/devalue — второе кратно сложнее и не даёт преимуществ.
2. **Metascore (по платформам) уже приходит вместе с карточкой игры одним запросом**
   (`.../product`), а **Userscore по платформе требует отдельного запроса на каждую
   платформу** (`.../platform/{slug}/stats/web`). Число внешних вызовов на одну игру
   линейно растёт от числа её платформ (у мультиплатформенных релизов — 4+ платформы
   ⇒ 4+ доп. вызова только ради userscore, и это без учёта самих текстов отзывов).
3. **Официальный YouTube API физически не может отдать транскрипт чужого видео**
   (OAuth + права владельца), а единственный рабочий (неофициальный) путь получения
   транскрипта систематически ломается именно на облачных серверных IP — том самом
   окружении, где почти наверняка будет жить этот сервис. Это единственный компонент
   всего ТЗ, для которого на сегодня нет гарантированно рабочего пути с типичного
   хостинга, и его нужно закладывать как деградируемую фичу (best-effort +
   явный статус "транскрипт недоступен"), а не как гарантированную.
4. **Пагинация "новых" игр не идемпотентна между заходами** (нет стабильного
   tie-break при одинаковой `releaseDate`) — обязательный дедуп по `id` игры в БД,
   недостаточно просто продвигать курсор `offset`/номер страницы.
5. **Готовые "summary"-эндпоинты отзывов** (`.../summary/web`, разбивка по
   `default/positive/negative/neutral`) уже дают отобранные цитаты без необходимости
   пагинировать весь список и вручную бакетировать по тональности — это может
   заметно упростить и удешевить пайплайн суммаризации критик/юзер-отзывов, если
   таких 7±N цитат на категорию окажется достаточно по ТЗ (иначе как fallback —
   полный список через `.../web` с учётом лимитов страницы из §3.1).
