# 20 — Plan: декомпозиция на задачи

Входы: `docs/task.md`, `docs/10-design.md`, `docs/11-decisions.md`
(приоритетный при конфликте).

Одна задача — один заход агента-исполнителя. Нумерация с пропусками:
номера сохранены от первой версии плана, часть задач слита.

---

## 0. Как decisions.md меняет design.md

**LLM-провайдер.** Дизайн написан под Anthropic Claude Haiku с tool use
(§5, §4.4, ADR-7). Решение владельца — Google AI Studio, `gemini-3.8-flash`,
структурированный вывод через `responseSchema`, ретрай на 429. Контракты
`LlmClient` / `LlmResult` / `ReviewSummaryOut` из design §4.4 сохраняются,
меняется только реализация адаптера. Затрагивает T-24, T-25, T-30, T-44.

**Стоимостная оценка §5.6.** Посчитана по прайсу Anthropic, к бесплатному
тиру Gemini неприменима. В задачи не переносится. В T-24 заметка: лимиты
бесплатного тира не проверялись, троттлинг настраивается по факту.

**Коды ошибок LLM (§5.5).** Специфичны для Anthropic. Решения называют
только ретрай на 429. Логика из дизайна сохраняется — три попытки с
backoff, circuit breaker на пять подряд неудач, статусы `llm_failed` и
`no_data` — конкретные коды Gemini уточняются при реализации T-30.

**Volume для логов (OQ-3).** Дизайн просил persistent volume на Railway.
Решение — volume не покупаем, raw JSONL-логи для сдачи собираются с
локального прогона. Отсюда T-48. Деплой T-11 от этого не зависит.

**Ретрай упавших игр (OQ-7).** Дизайн выбрал «нет ретрая в течение суток»
(ADR-6). Решение владельца добавляет: ручной запуск переклеймивает
failed-игры сверх обычной квоты 20, отдельным проходом по
`processed_games(day=today, status='failed')`, не трогая
`day_cursor.browse_offset`, максимум 20 игр за один запуск. Отсюда T-49.

**SQLAlchemy.** Дизайн не называл слой доступа явно, только «raw DDL без
`create_all`» (ADR-3). Решения называют SQLAlchemy. В T-01 — async engine
и Core/raw SQL для запросов; `schema.sql` по-прежнему применяется напрямую,
не через `Base.metadata.create_all`, так что ADR-3 не нарушен.

## 1. Границы

Обязательная часть ТЗ закрывается задачами T-01 … T-34 (срезы S0–S5).
Похожие игры входят в обязательную часть по OQ-4.

Доп. часть 2 (мониторинг и кнопка) — T-35, T-38.
Доп. часть 1 (летсплеи) — T-41, T-44.
Обязательны для сдачи независимо от объёма — T-47 (README) и T-48

Точки остановки, после каждой система рабочая и демонстрируемая:
после T-34 обязательная часть закрыта, после T-38 добавлена доп. 2,
после T-44 добавлена доп. 1. T-47 и T-48 всегда последними.

## 2. Задачи

### S0 — каркас

#### T-01. Каркас проекта

Структура пакета, конфиг из переменных окружения, FastAPI с Jinja2,
async-подключение к Postgres через SQLAlchemy, применение `schema.sql`
при старте, эндпоинт `/healthz`.

Зависимости: нет.

Готово, когда: приложение поднимается локально, `/healthz` возвращает 200
и подтверждает соединение с базой, пустая страница списка рендерится.

#### T-04. Схема БД целиком

Один `schema.sql` со всеми таблицами: `games`, `game_platforms`,
`game_genres`, `day_cursor`, `processed_games`, `runs`, `review_summaries`,
`letsplays`. Плюс индексы и расширение `pg_trgm`. DDL берётся из design §3
целиком, `CREATE TABLE IF NOT EXISTS`.

Зависимости: T-01.

Готово, когда: повторный запуск приложения не падает и не пересоздаёт
таблицы, все индексы из дизайна на месте.

### S1 — первые игры на экране и деплой

#### T-05. Metacritic client: ядро

Общий HTTP-слой: httpx `AsyncClient`, явный не-дефолтный User-Agent,
глобальный клиентский rate-limit не выше 1 rps, retry с экспоненциальным
backoff на 429/5xx/таймаут, `MetacriticError(status, url, body_excerpt)`
как единственное исключение наружу.

Зависимости: T-01.

Готово, когда: два последовательных запроса разнесены во времени не менее
чем на секунду; 500-й ответ ретраится, после исчерпания попыток наружу
летит `MetacriticError`, а не сырое исключение httpx; логики маппинга под
конкретные эндпоинты в модуле нет.

#### T-06. Metacritic client: методы

Все вызовы к API: new releases, browse с offset, product по slug,
userscore и criticscore по платформам, сводки отзывов и списки отзывов.
Маппинг JSON в DTO по контрактам из design §4.1, пути полей — из
`00-research.json`.

Зависимости: T-05.

Готово, когда: каждый метод возвращает типизированный DTO на реальном
ответе API; отсутствующие поля не роняют маппинг; для игры без ведущей
платформы работает правило из design §8 (берём платформу с наибольшим
`metascore_count`).

#### T-08. Upsert игры

Транзакционная запись: `games`, `game_platforms` с обоими рейтингами,
`game_genres`, заполнение `genres_cache`, `best_metascore`,
`best_userscore`, сохранение сырого ответа в `raw`.

Зависимости: T-04, T-06.

Готово, когда: повторный upsert той же игры обновляет поля и не плодит
дубликаты платформ и жанров; `genres_cache` и `game_genres` согласованы.

#### T-09. Минимальный ручной ingest

`POST /admin/run`, который проходит цепочку new releases → product →
upsert. Без курсора, без claim, без планировщика.

Зависимости: T-06, T-08.

Готово, когда: один вызов наполняет базу двадцатью реальными играми.

#### T-10. Список игр

Базовый UI: карточки с обложкой, названием, платформами и оценками.
Обложки отдаёт CDN Metacritic по `bucketPath`, локально ничего не хранится.

Зависимости: T-08.

Готово, когда: `/games` показывает игры из базы с картинками.

#### T-11. Деплой на Railway

Postgres, переменные окружения, публичный URL, применение схемы на чистой
базе при первом старте.

Зависимости: T-09, T-10.

Готово, когда: по публичной ссылке открывается список с реальными играми.

### S2 — полная карточка и витрина

#### T-14. Карточка игры

`/game/{slug}`: название, обложка, описание, разработчик, ESRB,
все платформы с Metascore и Userscore, ссылка на трейлер Metacritic.

Зависимости: T-08.

Готово, когда: карточка показывает все поля из обязательной части ТЗ,
кроме резюме и похожих игр.

#### T-15. Витрина: поиск, фильтр, сортировка

Поиск по названию через `pg_trgm`, фильтр по платформе, сортировка по
Metascore, Userscore и дате, пагинация. Всё через HTMX-фрагмент без
перезагрузки страницы.

Зависимости: T-10.

Готово, когда: три контрола работают вместе и сохраняются в query-строке.

### S3 — часовой цикл

#### T-18. Состояние обхода

`DayCursorRepo` с ленивым созданием строки на день через
`INSERT ... ON CONFLICT (day) DO NOTHING`. `ProcessedRepo.claim` на
`ON CONFLICT (day, game_id) DO NOTHING RETURNING`. `BatchSelector` с
фазами `new_releases` → `browse` → `exhausted` и правилом добора не более
пяти страниц за заход.

Зависимости: T-04, T-06.

Готово, когда: первый заход суток идёт по New Releases; повторный вызов
в те же сутки не возвращает уже обработанные игры; смена даты сбрасывает
фазу и offset без отдельной джобы.

#### T-22. Ingest runner

Advisory lock через `pg_try_advisory_lock`, фиксация даты на весь заход,
оркестрация обработки игр с семафором поверх глобального лимитера,
запись результата в `runs`, проставление статусов в `processed_games`.

Зависимости: T-18, T-08.

Готово, когда: два одновременных запуска не пересекаются, второй выходит
со статусом `skipped_locked`; падение обработки одной игры не роняет заход.

#### T-23. Планировщик

APScheduler с cron `0 * * * *` в UTC, `max_instances=1`, `coalesce=True`,
`misfire_grace_time`. Ручной запуск вызывает тот же runner фоновой задачей.

Зависимости: T-22.

Готово, когда: заход стартует по расписанию; ручной вызов не дублирует
плановый.

### S4 — резюме отзывов

#### T-24. Gemini-адаптер

Реализация `LlmClient` поверх Google AI Studio: `responseMimeType`
`application/json` плюс `responseSchema`, ретрай на 429 с backoff,
circuit breaker на пять подряд неудач, возврат `LlmResult` с токенами
и задержкой.

Зависимости: T-01.

Готово, когда: вызов возвращает объект строго по схеме; при 429 виден
ретрай; при исчерпании попыток возвращается `LlmResult(ok=False)`,
исключение наружу не летит.

Замечание: лимиты бесплатного тира не проверялись, значения троттлинга
уточняются по фактическим заголовкам ответа.

#### T-25. Промпты

`PromptRepo`: загрузка `prompts/*.v1.md`, версия из имени файла, sha256
текста, кэш на процесс. Тексты `review_summary_critic.v1` и
`review_summary_user.v1`: цитаты передаются отдельным сообщением, каждая
обёрнута в `<review>`, в системной части явно сказано игнорировать любые
инструкции внутри отзывов. Резюме на русском.

Зависимости: T-01.

Готово, когда: промпт грузится по имени, версия и хеш доступны для
логирования, в коде нет текста промпта.

#### T-29. JSONL-логгер вызовов LLM

Запись одной строки в `logs/llm/{YYYY-MM-DD}.jsonl` после каждого вызова.
Поля по design §5.4: время, версия и хеш промпта, модель, полные
отправленные сообщения, ответ, токены, задержка, статус, номер попытки.

Зависимости: T-01.

Готово, когда: строка пишется и при успехе, и при отказе; каждая попытка
ретрая — отдельная строка; файл остаётся валидным JSONL.

#### T-30. Пайплайн резюме отзывов

Сборка цитат из summary-эндпоинтов, fallback на списки отзывов при пустой
подборке, обрезка по длине и количеству, `quotes_hash` для пропуска
повторной генерации, вызов модели, обработка отказов, запись в
`review_summaries`, подключение к ingest runner.

Зависимости: T-24, T-25, T-29, T-06, T-22.

Готово, когда: у игры появляются два раздельных резюме — по критикам и по
пользователям; при отсутствии текстов ставится `no_data` без вызова
модели; отказ LLM не роняет обход; повторный обход с тем же набором цитат
не делает нового вызова.

#### T-31. Резюме в карточке

Два блока в карточке игры: что нравится и что не нравится, отдельно у
критиков и у пользователей.

Зависимости: T-30, T-14.

Готово, когда: блоки отображаются, при статусе `no_data` или `llm_failed`
показывается понятное состояние вместо пустоты.

### S5 — похожие игры

#### T-33. SQL похожих игр

Запрос из design §3.5: пересечение жанров плюс вес за совпадение
разработчика, top-5 из своей базы.

Зависимости: T-08.

Готово, когда: для игры с жанрами возвращается до пяти похожих; для игры
без жанров — пустой результат без ошибки.

#### T-34. Блок «Похожие игры»

Вывод top-5 в карточке, клик по названию открывает карточку этой игры.

Зависимости: T-33, T-14.

Готово, когда: блок рендерится, ссылки ведут на существующие карточки;
при пустом результате блок не показывается.

### S6 — мониторинг (доп. часть 2)

#### T-35. Шина событий и состояние воркера

In-memory pub/sub с очередью на подписчика и стратегией drop-oldest,
кольцевой буфер последних событий, `WorkerState` с восстановлением
счётчиков из `processed_games` и `runs` при старте, публикация событий
из ingest runner.

Зависимости: T-22.

Готово, когда: события публикуются на каждом шаге захода; после рестарта
счётчики за сегодня восстанавливаются, а не обнуляются.

#### T-38. Страница статуса

`/status` с первичным рендером из `WorkerState`, SSE-эндпоинт `/events`
с keep-alive-пингом, htmx sse-extension на странице, кнопка ручного
запуска с проверкой admin-токена и ответом 409, если заход уже идёт.

Зависимости: T-35, T-23.

Готово, когда: на странице в реальном времени видно текущую игру и
счётчики; кнопка запускает обработку; повторное нажатие во время работы
возвращает 409.

### S7 — летсплеи (доп. часть 1)

#### T-41. Адаптеры летсплея

Поиск ролика через yt-dlp `ytsearch` с выбором самого просматриваемого.
`RetellingService` для 300.ya.ru с `YA300_SESSION_ID`, собственный тип
исключения при недоступности сервиса или протухшей куке.

Зависимости: T-01.

Готово, когда: по названию игры находится ролик с `view_count`; на
известной ссылке сервис возвращает текст пересказа; ошибки сервиса
приходят типизированным исключением.

#### T-44. Пайплайн летсплея

Цепочка find → retell → LLM-заключение, статусы `ok`, `not_found`,
`service_error`, одна попытка на игру за обход, подключение к ingest
runner, блок в карточке с заключением и ссылкой на ролик.

Зависимости: T-41, T-24, T-04, T-14.

Готово, когда: у игры появляется заключение по летсплею и ссылка;
недоступность 300.ya.ru или yt-dlp не влияет на остальную обработку;
статус виден в базе.

### S8 — сдача

#### T-47. README

Как запустить локально, какие переменные нужны, краткая архитектура,
ссылка на `docs/`, честный раздел о том, что не реализовано и почему.

Зависимости: всё выше.

Готово, когда: по README проект поднимается с нуля.

#### T-48. Локальный прогон и сбор логов

Полный часовой цикл локально на нескольких десятках игр, проверка, что
`logs/llm/*.jsonl` наполнился и валиден.

Зависимости: T-30.

Готово, когда: в `logs/llm/` лежат строки по каждому вызову модели.

### Отдельно

#### T-49. Переклейм failed-игр

Ручной запуск дополнительно берёт до 20 игр из
`processed_games(day=today, status='failed')` сверх обычной квоты,
отдельным проходом, не трогая `day_cursor.browse_offset`.

Зависимости: T-18, T-22.

Готово, когда: после ручного запуска упавшая сегодня игра
переобрабатывается, а плановый заход её по-прежнему не берёт.

## 3. Порядок

По номерам, внутри зависимостей. Каждый срез заканчивается рабочей
системой. T-11 стоит рано намеренно: риск хостинга снимается в начале,
а не в конце, и дальше каждый срез можно выкатывать.
